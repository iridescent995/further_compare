# Document text comparison in CLI and desktop batches

Status updated 2026-10-22: the core CLI/native-batch increment below shipped in **2.195.0**, now installed after both Mac packages passed acceptance. The standalone Node backend was verified from the repository on this Mac. The original design and wider validation goals are retained below; they are not all completion claims.

## Scope and concrete gap

The user requested full comparison-product functionality, including other comparison types. PDF and Office text conversion belong to the recorded document-comparison scope in [the text capability assessment](text-next-plan.md). The current [PDF](pdf-text.md), [DOCX](docx-text.md) and [CLI](cli.md) documents establish the implemented boundaries. This next step makes those existing PDF/DOCX projections usable in scripted text comparisons; it does not introduce an unrelated comparison type.

At the planning baseline, `scripts/compare.cjs:main` read text inputs with the ordinary 10 MiB limit and calls `decodeText` directly. `scripts/batch.cjs:runPlannedJobs` calls that function; `desktop/batch-service.cjs` has no extraction dependency and forwards directly to it. Consequently a PDF/DOCX opened successfully in the UI did not receive the same conversion in either CLI or desktop batch. The UI's shared `src/text-input.cjs` already provides the right projection contract, including validation and no binary fallback.

Folder CLI mode remains SHA-256 snapshot comparison. Binary mode remains exact bytes. Table mode remains CSV/TSV parsing. Do not silently convert these modes. “Office” here means the shipped DOCX main-document projection, not XLS/XLSX, PPT/PPTX, RTF, ODT or legacy DOC conversion. Those broader formats remain separate parity work, as do OCR, visual PDF comparison and arbitrary user converters. This milestone must not be described as complete Office support.

## Original design: shared comparison boundary

1. Make text-mode reads select 32 MiB only for recognized `.docx`/`.pdf` names; retain ordinary text's 10 MiB limit. Read each input into an immutable bounded byte snapshot before extraction. Reuse the native snapshot reader's descriptor/identity checks, or extract a platform-neutral equivalent; retain captured hash/length and check for changes before publishing a report. Neither comparison nor extraction receives write authority over inputs.
2. Replace direct decoding with awaited `decodeTextInput(bytes, name, encoding, {extractPdfText, signal})`. Supply extraction through trusted programmatic options, never a converter command/path from batch JSON. Document conversion failures are errors, never binary fallback or empty successful comparisons. One side may be a projection and the other ordinary text.
3. Apply existing profiles, ignored patterns, grammar and whitespace rules to extracted text after conversion. Keep original extracted rows in reports. An explicit non-`auto` input encoding for a document side should fail clearly rather than pretend it controls PDF/DOCX extraction; ordinary sides retain existing encoding behavior. Batch dry-run validates this rule from recognized filenames.
4. Keep the public text comparison result computation separate from report publication so all extraction/validation completes before creating an output. Preserve exclusive creation (`wx`), existing-file refusal, batch destination uniqueness and input-tree exclusion. Remove only a newly created, still-owned partial report if writing fails; never remove a pre-existing or replaced destination. Do not add document writeback, save tokens, or PDF/DOCX export from projected text.

Suggested injection: `main(argv, {extractPdfText, signal, ...existingRuleOptions})`; `runBatch`/`runPlannedJobs` forward trusted runtime dependencies separately from jobs. No callback or runtime path is serialized into the reviewed batch plan.

## Native desktop batch adapter

Construct each window's `BatchService` with the runtime's existing PDF adapter and lifetime cancellation signal. Its `execute` forwards those dependencies to `runPlannedJobs`. Reuse `desktop/pdf-text-service.cjs`: lazy sandboxed hidden renderer, bundled PDF.js and module worker, local resource allowlist, 30-second active deadline, bounded queue and validated result. Do not create a second unbounded parser in Electron's main process, and do not make the native path depend on a new Node canvas binary.

Keep preview read-only: no extraction window, worker, font access or report creation. Include resolved conversion kinds and limitations in preview, binding them to the reviewed plan. Existing changed-plan detection still applies; input snapshots describe execution-time bytes, not a promise that preview pinned their contents. On owner closure abort extraction and prevent subsequent jobs or reports. A completed report is retained; remaining jobs are explicitly unattempted/cancelled. Ordinary per-job decoding failures still allow later jobs to run, preserving existing batch semantics.

## Plain Node CLI PDF backend

Plain Node operation must remain supported without Electron, a desktop session, a browser download, an external service or fabricated DOM globals. DOCX can already use the real XML parser in `text-input.cjs`; route it first and keep plain-text startup lazy and unchanged.

The pinned installed `pdfjs-dist/legacy/build/pdf.mjs` attempts to obtain real DOMMatrix/Path2D from `@napi-rs/canvas`, and creates a DOMMatrix at module initialization. The recorded Node spike failed without that dependency. Its Node PDFWorker also uses an in-process message handler, so merely constructing PDFWorker does not provide a terminable isolation boundary.

The next concrete feasibility task is a standalone Node extraction child process using the pinned legacy PDF.js entry and a verified compatible genuine `@napi-rs/canvas` runtime. Do not add that dependency to the release until its supported Node 24/platform binaries, license, install behavior and actual text fixtures pass. Missing support must produce `DOCUMENT_ENGINE_UNAVAILABLE` for PDF only; plain text, binary, tables, snapshots and DOCX must still run. This is a staged implementation gate, not a claim that Node PDF is already supported.

The parent owns a hard 30-second timer including child startup/import. Send copied bytes through a bounded framed pipe or advanced child IPC, not argv/environment/base64 shell commands; cap input at 32 MiB and response at 8 MiB text plus bounded metadata. Kill and reap on timeout/abort, suppress engine chatter on result stdout, and always dispose processes. Bound concurrency to one extraction per CLI invocation and sequential batch execution. The child may use PDF.js's internal Node message handler because the entire child is externally terminable; do not mislabel that handler a separate OS worker. This boundary is not an OS sandbox or strict memory ceiling.

Refactor only the platform-neutral page/text loop and options from `src/pdf-text-extractor.js`: accept an injected binary-resource factory. Browser keeps its bounded XHR factory; Node uses a fixed-package-root filesystem factory with the same filename/extension allowlist, per-resource bound, no URL/network fallback, and latched failure even if PDF.js swallows resource errors. Reuse identical engine/version, page/item/output limits, page separators, exclusions and strict projection validation. Do not introduce rendering, attachment execution, PDF scripts, system fonts or remote fetches. Test equivalence against the current browser/native adapter before publishing Node support.

If the genuine Node backend proves unavailable on a target, document that specific limitation and keep native desktop batch PDF working. Do not silently auto-launch an installed Electron app or pretend a missing backend is a successful comparison. An explicit packaged command-line Electron mode could be a later independently designed fallback, but is not needed to preserve the ordinary Node commands.

## Reports, errors and cancellation

- Preserve exit codes: 0 means comparable text equal under requested rules; 1 means differences with a valid report; 2 means usage, extraction, bounds, cancellation or report I/O failure. Preserve a single JSON report on stdout and diagnostics on stderr. No successful report after extraction failure.
- Add optional `documentProjections: {left?, right?}` using the existing strict metadata union. `sourceFormats` remains the format of the compared text, not the binary document encoding. Add captured source byte length/SHA-256 separately, explicitly named as input identity. Reports must say “Equivalent extracted text” for equal projections, never imply byte/layout identity. Text/HTML must display projection kinds, coverage and exclusions, not merely bury them in JSON. Escape filenames and extracted content as today.
- Keep report version 1 with additive optional fields if existing readers accept unknown fields; test known consumers before choosing this. Do not alter ordinary report fields or require provenance for old saved reports. A schema-breaking change requires a separately versioned contract.
- Normalize document errors to bounded stable codes (`DOCUMENT_ENGINE_UNAVAILABLE`, `DOCUMENT_PASSWORD_REQUIRED`, `DOCUMENT_NO_TEXT`, `DOCUMENT_INVALID`, `DOCUMENT_LIMIT`, `DOCUMENT_RESOURCE`, `DOCUMENT_TIMEOUT`, `DOCUMENT_CANCELLED`) plus readable messages. The adapters currently throw message-based Errors, so structured codes need explicit mapping at the extraction boundary rather than fragile string parsing in the CLI. Preserve existing filesystem error codes.
- Batch job results retain same/different/error. User cancellation stops scheduling and marks remaining jobs cancelled/unattempted explicitly; ordinary job failure continues. Global exit is 2 when either happens. Successful prior reports remain. SIGINT/SIGTERM handling must abort and reap children, avoid new outputs, and use the documented CLI cancellation exit policy (2), with focused signal tests.

## Implementation and acceptance sequence

1. Shared DOCX/adapter routing and report provenance: add CLI fixtures for DOCX↔DOCX, DOCX↔TXT, ordinary encoding regression, invalid DOCX, a compressed document over 10 MiB within 32 MiB, mixed documents, and explicit document-encoding rejection. Verify originals by hash and existing output refusal. Use injected PDF adapters for contract tests, clearly not real PDF acceptance.
2. Desktop batch integration: real PDF and DOCX fixtures through preview/execute; verify actual local extraction, report labels/provenance, same/different/error, continued jobs after malformed/image-only/password-required files, changed review rejection, close/abort and no late report. Test both Mac packaged architectures after coordinated build; Windows runtime remains deferred.
3. Node feasibility and bounded transport: genuine engine and dependencies in child process; multilingual/CMap/font fixtures, Unicode, multi-page and partial-empty metadata, malformed/password-required/image-only refusal, startup hangs, parser hangs, crash, oversized framed output, abort and child cleanup. Assert no network access and no fake DOM stubs; plain Node commands must work with the PDF backend absent.
4. Real CLI and JSON batch end-to-end: compare actual PDF↔PDF/PDF↔TXT/DOCX↔PDF, projection parity across adapters, JSON/text/HTML escaped output, limits, reports containing extracted rather than compressed bytes, input change during extraction, report destination races, partial write ownership, successful reports retained after a later failure. Confirm dry run creates no process or output.
5. Regression suites: `test/batch.test.cjs`, `batch-encoding.test.cjs`, `batch-desktop.cjs`, text grammar/profile/whitespace/case/ignored-pattern CLI tests; existing PDF extraction/service/routing/native suites. Verify packaged modules and assets separately from runtime tests. No release completion claim until the real adapters, not only injected doubles, pass their applicable acceptance.

Original first-step plan after 2.194 verification: shared DOCX routing plus trusted adapter plumbing into native batch, with report metadata and focused CLI tests. The Node PDF dependency spike can proceed independently; its results determine the next implementation step without blocking already supported ordinary Node modes.

## Shipped 2.195.0 milestone and remaining gates

The shared route now uses `decodeTextInput` with trusted extraction/signal options, bounded local source snapshots and revalidation. DOCX and injected/native PDF conversion work in comparison and batch execution. The genuine Node backend is also implemented and lazily selected for PDF when no trusted adapter is supplied. Batch JSON cannot supply converters, filesystem resource roots or callbacks. Preview contains kind/scope/limitations descriptors without extraction.

Reports remain version 1 with additive document provenance and input byte/hash identity. Text/HTML identify extracted-text meaning and exclusions. Encoding overrides for document sides reject. Exclusive report publication binds the destination directory before conversion, verifies output bytes and final path/descriptor identity, and preserves foreign replacements or edits on failure. SIGINT/SIGTERM and native Stop/window closure cancel work; batch retains prior successes and marks remaining jobs cancelled/unattempted. Ordinary per-job failures still continue.

The Node adapter is `src/pdf-text-node.cjs`, backed by a fixed child and shared `src/pdf-text-core.mjs`. It uses genuine installed PDF.js/canvas, bounded binary frames, a startup-inclusive 30-second deadline and kill/reap cancellation. Missing backend availability affects PDF only. The child is not an OS sandbox or strict memory ceiling.

Evidence: the final CLI/batch regression run passed 40/40 tests, terminal 0, `/private/tmp/fc-document-cli-final.log`. Tests include actual Unicode PDF/PDF, PDF/text and PDF/DOCX, DOCX above the ordinary text limit, malformed/image-only rejection, injected adapter/source-change checks, HTML escaping, dry-run, missing backend, executable signals and publication races. Native batch/service and shared extraction evidence is recorded separately; release acceptance is separately recorded below.

Remaining gates include cross-platform runtime validation (Windows expressly deferred), wider real-world reading-order/CMap coverage and any adversarial cases from the original sequence not covered by named tests. OCR, visual PDF comparison, other Office formats, arbitrary converters and full product parity remain separate work.

# Next Windows Explorer integration work

Plan reviewed against `implementation-plan.json` (`windowsIntegration2187`), current source, and Microsoft documentation on 2026-10-22. Windows execution testing remains explicitly deferred by the user; no Windows machine is required to continue planning or platform-independent implementation. Mac integration is outside this plan.

## What ships today

- Per-user classic Explorer submenu for files (`HKCU\\Software\\Classes\\*`) and folders (`Directory`), generated by `desktop/native/shell-menu.ps1`: **Set as Left**, **Compare with Left**, **Clear Left Selection**.
- Commands target the configured `Further Compare.exe`; all verbs have `MultiSelectModel=Single`. Windows 11 users are directed to **Show more options** by `src/shell-setup.js`.
- Owned-key preflight prevents modifying unrelated registrations. `desktop/windows-shell-integration.cjs` serializes operations per application, inspects fresh registry state after every mutation, and validates installed/partial/stale responses. These mechanisms have injected regression tests and package checks; they have not been exercised on Windows in this session.
- `desktop/shell-requests.cjs` already supports two selected items, same-kind validation, remembered left selection, pair-order review, and safe new-tab opening. Windows currently has no Explorer selection-array transport that supplies that pair.
- Distribution is an unsigned x64 ZIP (`pack:win`, `build.win.signExecutable=false`). No compiled Windows native COM extension or sparse package installer ships in that release. Subsequent source work is recorded below. Local PATH inspection found no `clang-cl`, MinGW compiler, or CMake, and this Mac is not evidence of Windows SDK availability.

## Prioritized implementation

| P0 | Selection policy and exact dispatch contract | Add an independently testable native policy/request layer under `desktop/native/explorer/`. One filesystem item: Set as Left and Compare with Left. Exactly two files or two folders: Compare Selected. Mixed kinds, virtual items, zero or >2 items: disabled/hidden with a clear reason. | P0 | Fixed-host launch | Reuse existing `--fc-set-left`, `--fc-compare-left`, and `--fc-compare-selected` argument semantics through an explicitly resolved installed executable. Use `CreateProcessW` with a non-null executable path and tested Windows argument quoting, never cmd/PowerShell, a default protocol handler, or an executable found on PATH. | P1 | Build and distribution | Add reproducible C++/Windows SDK build instructions and project, embed native binary/manifest artifacts, validate architecture and packaging paths, then add signing and sparse package deployment artifacts. | P2 | Polish and coexistence | Make enabled/disabled states and explanatory text accessible; add icons consistent with the app, cap filename labels, handle high contrast/DPI/localization, and prevent duplicate modern/classic entries where possible. ## Verification gates

**Can implement now:** policy tests, hostile/Unicode filename and Windows quoting vectors, selection-copy immutability tests, bounded hint schema/atomic writer, injected lifecycle failure/serialization tests, manifest/source review, and host command routing regressions. Keep Windows-specific path handling injectable so tests on macOS do not accidentally use POSIX `path.isAbsolute` semantics.

**Requires a Windows SDK toolchain:** real COM compilation/linking, ABI validation, manifest validation, package generation/signing verification, and artifact architecture checks. A source-only pass is not a compiled native extension. Toolchain acquisition/build infrastructure is a dependency, not proof of runtime behavior.

**Windows runtime explicitly deferred:** actual Windows 11 primary-menu placement, Explorer COM loading/callback threading and submenu behavior, selection ordering, long/UNC paths and cloud placeholders, cold/warm launches, filename refresh, rapid repeated invocations, dirty-tab preservation, upgrade/move/repair/uninstall, and default-user/non-admin deployment. Also exercise classic fallback on Windows 10/11. Leave the native feature labeled experimental/not runtime-verified until these gates are completed; do not request a Windows machine again unless the user reopens that decision.

Current next implementable slice: authoritative package inspection, durable recovery storage and guarded lifecycle adapters; portable policy and native COM source now exist. Do not block that work on Windows runtime access, and do not advertise modern-menu support merely from source/static checks.

## Discoverable recovery history

The journal now exposes `discover()` so a later application startup can find prior operation IDs without keeping a second UUID index. Discovery validates the existing private-directory, identity/link, snapshot sequence and hash-chain rules. It reports `unpublished`, `unfinished-history` or `verified-history` summaries, never replay instructions or mutation authority. Even verified history requires fresh inspection; it does not prove current installation or menu activation. Pending-only crash directories remain visible as unresolved history.

The lifecycle runner accepts an optional `discoverJournals` callback. Its status path combines fresh authoritative installation inspection with these recovery summaries. Corrupt or incomplete discovery blocks recovery status with `recovery-discovery-failed` while retaining the freshly inspected snapshot. Install/repair/uninstall behavior and native capability gates are unchanged. This is a connected orchestration foundation; no new application IPC, automatic replay, or native activation is enabled.

Discovery refuses more than 256 operation directories, 4,096 snapshot/pending files, or 32 MiB of aggregate snapshot bytes. Initial and final directory inventories use bounded `opendir` reads, stopping after the cap plus one entry and closing handles on every exit; they never allocate an unrestricted `readdir` result. It does not truncate results and label them complete. Queued writes are awaited per operation; root identity, the complete root directory-name inventory and each operation’s filename inventory are checked again before returning. Every file must still match its budgeted preflight stat before opening. Reads allocate only that preflight size plus one sentinel byte and use bounded handle reads, so concurrent growth cannot turn a small budgeted snapshot into an unbounded allocation. Historical records may change after inspection, so summaries are not current mutation bindings. POSIX private-mode checks still do not establish Windows ACL safety.

Portable tests cover real filesystem histories, pending directories, corruption, foreign/symlink entries, aggregate byte/file/work limits, queued persistence, concurrent root changes and the actual lifecycle runner status path. No Windows runtime or SDK-asset claim follows from these tests.

## Application status integration

The File Manager Integration dialog now has a separate Windows-only **Modern Explorer menu** status section. A per-application serialized service exposes status inspection through a dedicated IPC handler; requests other than `status` are rejected. Classic integration retains its existing controls. No modern enable, repair or removal controls are exposed while signed native assets and activation acceptance remain unavailable.

The service reads only `desktop/explorer-release.json` inside the packaged application, with an exact version-1 schema (`version`, `packageName`, `publisher`, `helperSha256`) and a 4 KiB bound. This file is intentionally absent from current releases: no publisher identity or helper hash is fabricated. Missing configuration produces actionable classic-menu guidance without launching PowerShell. When a future release supplies configuration and the fixed executable, DLL, MSIX and helper assets, the service connects existing collection, attestation and read-only assessment. Missing assets, invalid configuration, inspection failure, partial/moved registration and conflicts remain distinct; registration never claims menu activation.

Recovery discovery uses the fixed `explorer-recovery` directory under application user data. Only operation counts and unresolved-history counts cross IPC. Failure to read history remains visible independently of component inspection. Neither raw journal records, file paths, registry data nor lifecycle snapshots are returned to the renderer. History cannot authorize replay, mutation or activation. Windows ACL verification and real Windows execution remain deferred limitations.

Source verification: `test/windows-explorer-integration.test.cjs` covers missing/invalid configuration, unsupported builds, assets, bounded summaries, shared serialization and failures; `test/shell-setup-browser.cjs` covers the Windows status section alongside existing Finder/Services interactions. These tests do not constitute Windows native runtime acceptance.

The app-connected read-only status service and UI ship in 2.201.0. Production configuration/native SDK assets remain absent, so the app accurately offers classic integration without invoking modern native inspection. Activation and lifecycle mutations remain pending. All 38 focused composition tests and the shell-setup browser regression passed; Windows execution remains deferred.

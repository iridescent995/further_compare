# Explorer package attestation transport

Source implementation only. No helper binary was compiled, signed, packaged or run on Windows. No registration, enabling, registry mutation or application wiring was performed.

`desktop/windows-explorer-attestation.cjs` combines the existing read-only collector with `FurtherComparePackageInspection.exe`. Configuration supplies a trusted package name, publisher, installation directory and helper SHA-256; these must come from reviewed release metadata, never registry observations or the helper's own response. The only helper location is that installation directory's fixed sibling executable. The collector is injectable and remains independently unverified.

The default transport invokes the fixed `desktop/native/explorer-attestation.ps1` through System32 Windows PowerShell without a command shell. The launcher rejects reparse files/ancestors, opens the helper with read sharing only, hashes the held bytes, checks Authenticode validity and exact publisher, then invokes only package or external-location modes. It retains the file handle through execution. Output is streamed into bounded buffers (65,536 characters stdout, 8,192 stderr), the helper receives a 30-second deadline, and timeout/error cleanup kills and waits for its process. Node independently caps captured output to 65,536 bytes and invocation time to 40 seconds. This is a bounded read-only launcher, not an OS memory sandbox; helper descendants are not expected or authorized by its design. A Windows job-object boundary remains necessary if hard process-memory/tree guarantees are required.

For injected tests, `withVerifiedHelper(path, expected, callback)` substitutes the launcher lease and must keep verified bytes immutable throughout callback execution. `execFile` is also injectable. Test-only evidence does not become runnable installation authority.

The consumer requires signed/hash-bound host, DLL and sparse package observations; the package helper must attest its exact path/hash, Windows-derived identity, generic manifest, block map and exact product COM/verb/external-content binding. Candidate identity and host architecture must agree. External-location evidence is joined only to an observed package with exactly that attested full identity. Older or unmatched registrations remain unverified; a location alone never proves ownership. A moved external location is retained as evidence for later conflict policy, never silently corrected. Fresh collector evidence must exactly match the immutable initial snapshot after helper calls, otherwise the whole inspection fails.

Results deliberately have `inspectionOnly:true`, `verified:false` and `activation:'unknown'`. They are not shaped as lifecycle-runner snapshots and cannot grant install, repair or uninstall authority. The existing observation collector and planner were not changed. Before a consumer may produce mutation authority, the SDK bridge and PowerShell launcher require Windows compilation/runtime acceptance, deployment of a signed pinned helper, runtime verification of held-file/timeout behavior, and a reviewed adapter mapping all unmatched/conflicting observations into the lifecycle policy. Missing helper/signature/hash/resource or changed observations fail inspection; no fallback to unsigned parsing exists.

Validation here: injected JavaScript tests verify exact invocation, immutable evidence, serialization, mismatched signatures/hash/product/identity/location refusal, stale inspection rejection and non-Windows no-op. Source assertions check launcher read-only APIs and bounds. These checks do not prove Windows PowerShell parsing, SDK ABI/linking, signature policy or actual registered external-location behavior.

Transport review corrections: an absent registry key's real collector shape is `{exists:false}` and is accepted without a fabricated values object; any contradictory owned values are rejected. The default launcher now emits a versioned `helper-invocation` envelope containing its actual held-file path, computed digest and verified certificate subject, together with the parsed helper result. The JavaScript consumer validates every envelope and records `helperInvocations` with `lockScope:'invocation'`; it no longer synthesizes signature/lock evidence from expected configuration or implies a single lock spans collection. PowerShell explicitly uses strict UTF-8 for child stdout/stderr and its own output; Node requests raw bytes and decodes UTF-8 fatally. Twelve injected/source tests pass, including Unicode paths/publishers, malformed UTF-8, contradictory proof and the fresh-install schema. Windows execution is still unverified.

## Read-only lifecycle assessment

The current source adds `desktop/windows-explorer-evidence.cjs`. Its factory connects collection, attestation and the existing lifecycle status planner. It returns fresh/partial/registered/moved/conflicting assessments while preserving raw conflicts and older or unmatched registrations. The normalized planner snapshot stays private; install, repair, uninstall and activation capabilities remain false. This is not application activation or a replacement for the Windows SDK/signing gates. Seven focused tests and 31 combined evidence/attestation/lifecycle tests passed in `/private/tmp/fc-windows-explorer-evidence.log`.

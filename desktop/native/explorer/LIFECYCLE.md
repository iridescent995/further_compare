# Modern Explorer lifecycle policy

`desktop/windows-explorer-lifecycle.cjs` is a pure planner. It does not query Windows, register packages, write registry values, or claim menu activation. `planWindowsExplorerLifecycle(action, snapshot)` accepts `status`, `install`, `repair`, or `uninstall`; it returns an allowed/blocked plan, concrete ordered steps, a digest of the inspected snapshot, registration status, asset issues, and `activation: 'unknown'`.

The trusted inspection adapter must supply:

- `expected.identity`: independently verified package name, publisher, familyName, fullName, four-component version, architecture (`x64`/`arm64`), and `verified: true`. Verify these against the signed manifest, not a caller assertion.
- `expected.executable`, `dll`, `packagePath`: canonical absolute local drive paths. The host and DLL must be siblings with the fixed product basenames.
- `expected.assets`: executable, dll, and package records with exact path, existence, valid signature evidence, matching publisher and SHA-256. Verify all required package assets/manifest through the Windows SDK and package verifier before asserting this evidence.
- `observed`: platform, integer Windows build, native architecture, complete current-user package inventory relevant to this identity, explicit `conflicts` array (including foreign CLSID/verb or competing identity ownership), and config `{exists, values}`. Registry values are `{type,value}` with exact `DWORD` / `REG_SZ` types. Package observations require verified publisher, architecture, full/family identity and resolved external content location.

Ownership uses `HKCU\Software\FurtherCompare\Explorer`: `OwnerVersion` DWORD1, `Executable` REG_SZ, `PackageFamilyName` REG_SZ, `PackageFullName` REG_SZ. These extend the existing hint transport contract. An owned minimal legacy config may be completed only without an already-registered unbound package. A matching registered package is never adopted without its existing ownership binding. Foreign, ambiguous, malformed or mismatched-location records block mutation.

Install checks Windows 11 build/architecture and all signed assets. It writes guarded ownership intent before registration, so an interrupted installation remains repairable, then registers the exact signed sparse package with exact external location and verifies package/config observations. Ownership intent alone is not registration evidence. Healthy installations produce verification-only plans. Repair can relocate or upgrade an exact owned package; its removal targets only the observed full package identity/location, then config intent is updated and the new package registered. Relocation clears stale display hints. Repair must never remove foreign registrations to make progress.

Uninstall does not require the old files to remain present or signed. It requires the inspected ownership binding and identity/location match, removes only that exact package, removes only the named product values (preserving unknown values), and verifies absence. It does not delete the application, DLL, unrelated keys, or package files.

## Execution adapter gate

No execution adapter exists yet. Source implementation and injected tests may proceed without a Windows runtime. Before shipping or enabling the adapter, require Windows SDK build/COM tests, signed package and asset validation, assigned publisher identity, and actual Windows acceptance. The adapter must re-inspect immediately before mutation and compare the snapshot digest; reject changed evidence. Each step must enforce its own ownership/identity/location guard, rehash deployment assets before registering, and inspect the result even when an operation reports failure. After any failure, stop and obtain a fresh plan; never continue subsequent steps blindly. Pending ownership intent permits repair after registration fails. Unknown registry values must survive cleanup. A package being registered is not proof Explorer loaded the DLL or displayed its menu; real menu/callback/host-launch checks remain separate.

## Repair interruption and recovery

A repair that replaces an existing registration is explicitly non-atomic. Its plan contains `recovery.atomic: false`, a required durable journal recording the inspected old package/config and intended new identity before the first mutation, and phase-specific failure rules. After removing the old registration, a failure leaves an owned partial installation; after writing new intent, repair can resume against that intent. After any registration error, inspect Windows because the package may actually have been registered. Do not report successful rollback merely because an API failed.

The planner offers rollback candidates only when `expected.previousDeployment` contains independently verified old identity and signed, hashed old executable, DLL and sparse-package assets at the original owned location. Otherwise rollback is explicitly unavailable and the UI must report repair-needed partial state. Candidate rollback steps require a fresh inspection, the durable operation journal, and no foreign registration; they remove only an exact newly owned registration, restore the old owned binding, register the verified old package and verify it. Rehash every old asset immediately before using it. Never execute these candidates directly from stale evidence or delete unknown registry values. Tests cover failure phases and missing/invalid old deployment evidence. No adapter or automatic rollback is implemented here.
